# 为生物学中的智能体铺平道路

*作者：Laura Luebbert。基于 Ferdous Nasri、Sarah Gurev、Patrick Varilly、Krithik Ramesh、Nuala A. O'Leary、Jonah Cool、Bernhard Y. Renard、Pardis Sabeti 和 Laura Luebbert 的[研究](https://arxiv.org/pdf/2606.06749)。*

---

在这篇文章中，Laura Luebbert 认为我们需要让生物学数据基础设施对智能体更加友好。作为一个案例研究，她和她的团队让科学研究智能体（Claude、Biomni、Edison Analysis、GPT）从 NCBI Virus——一个病毒学家用于监测和诊断试剂开发等任务的数据库——中检索序列数据。即使是最强的模型也不能始终如一地达到可靠数据集构建所需的准确率。但当她和她团队添加了 gget virus（一个确定性检索层）后，准确率几乎上升到了 100%。对科学智能体更广泛的启示是：确定性检索工具（目前）对于让智能体工作流更加可靠至关重要，生物学数据库需要将智能体视为规模化用户来设计。

使用 AI 智能体来导航生物学数据基础设施，就像开车穿行在一座在汽车出现之前就设计好的古城：基础设施可能是美丽的，甚至是经过深思熟虑的，但充满了狭窄、蜿蜒的街道，现代交通工具难以驾驭（古怪的文件格式、分散的数据库、一次性的检索脚本）。¹ 而软件基础设施则基本上是为汽车（智能体）的需求而设计的：铺设好的道路、清晰的车道、标准化的信号，以及为从起点到终点的快速通行而设计的系统（版本控制、文档完善的 API 和包管理器）。

因此，编码智能体的进步比生物智能体快得多。软件通常提供结构化的数字工作流和可靠的接口，而数据检索和验证所需的计算生物学基础设施往往是脆弱的、异构的，且依赖于特定流程。我们用来导航它们的工具必然是定制的，并为特定领域或假说而调整。此外，软件提供了可测试的输出，可以快速编译和验证（例如，通过生成一个通过项目测试集的补丁来解决 GitHub issue），而生物学提供的简单、可验证且有意义的奖励信号却很少。

因此，生物智能体的瓶颈不仅在于推理能力，还在于缺乏广泛可用的确定性执行层来查询生物数据。科学家可以表达他们的意图（例如，找到所有具有该结构域的人类激酶并提取其结构），但智能体往往缺乏可靠的方式来访问包含所需信息的数据库。

在生物学和科学工作流中，即使是小错误也可能产生严重后果。例如，从错误的基因组版本中检索坐标，可能使下游的生物学解释失效。无意中将 RefSeq 和 GenBank 记录混在一起、将部分基因组当作完整基因组处理、在分段病毒中混淆片段名称，或者因为元数据字段不一致而遗漏相关记录，同样会产生严重后果。研究的美妙与挑战在于，细节往往至关重要。

就像开车穿行在意大利的山区小镇，无论车有多强大，如果街道太窄、弯道太急、路线依赖当地知识，那都没用。如果我们想让智能体帮助科学发现——从疫情应对到药物设计再到生物建模——我们需要构建让它们能像人类一样可靠地导航的生物数据基础设施。

## Karpathy 关于网络开发的演讲告诉了我们什么关于用 AI 智能体做生物学的事

智能体需求与人类构建的工具之间的这种不匹配并非生物学独有。无论在哪里将智能体插入到仅为人类使用的环境中，同样的摩擦都会出现。

几个月前，Andrej Karpathy 做了一个关于 AI 时代软件的[演讲](https://www.youtube.com/watch?v=LCEmiRjPEtQ)，最后抱怨了一些听起来非常熟悉的事情。他用 vibe-coding 做了一个小型网络应用，但当他试图将其变成真正的产品时（身份验证、支付、部署），他在浏览器仪表盘中点击了一整周。

正如他总结的："代码是最简单的部分！大部分工作都在浏览器里，点击东西。"文档一直告诉他"去这个 URL，点击这个下拉菜单"。他的结论是没有人应该做这些事。相反，我们必须为智能体而构建。

Karpathy 在软件智能体世界中经历的，正是生物学研究人员长期以来一直在挣扎的事情：试图让智能系统在围绕异构信息、隐含约定和人类在浏览器中点击而构建的环境中运行的痛苦。

## 案例研究：病毒学中的"点击税"

远在 AI 智能体出现之前，计算生物学家和遗传学家就已经开始生产传统计算生物学的工具，逐步解决这个问题。Biopython、BioPerl、BioJulia、Entrez Direct、BioMart、gget 等工作流库都是为了将生物数据从浏览器界面转移到研究者可以直接计算的地方所做的努力。

问题在于，生物数据并不存在于拥有单一接口的单一数据库中。它是一个杂乱的道路网络，每条路都有自己的标识符、约定、格式、过滤逻辑和程序化访问程度。有些数据可以很容易地通过编程方式访问。而另一些则不然。

病毒学尤其属于较难的情况。从疫苗和诊断试剂设计到为蛋白质模型构建训练数据的研究工作流，通常始于从 NCBI Virus 检索序列——这是一个在可搜索的 Web 界面背后，汇集了来自 GenBank、RefSeq 和国际 INSDC 生态系统（包括 Pathoplexus）的病毒序列记录的集合。作为构建病毒疫情爆发监测工具的研究者，我们深知这些检索背后隐藏着多少专业知识。在病毒学实验室中，NCBI Virus 的数据集整理说明通常以复杂过滤器的长列表形式在研究人员之间传递，用户必须在 Web 界面中手动复现这些过滤器：正是 Karpathy 所抱怨的那种浏览器点击式工作流。

刚果民主共和国当前由本迪布焦病毒引起的埃博拉疾病疫情，是一个有力的例子，说明简化的病毒数据访问如何具有真实世界的生死攸关的后果。2026 年 5 月 14 日，位于 DRC 的 INRB金沙萨分析了 13 份血液样本，第二天确认了其中 8 份为本迪布焦病毒疾病，² 随后宣布了埃博拉疫情。到 5 月 29 日，世卫组织已报告 DRC 有超过 1,000 例确诊和疑似病例，包括超过 200 例死亡。研究人员还生成了首批接近完整的疫情爆发基因组，帮助确定此次疫情是由一次新的溢出事件引起的。

这些基因组向公共卫生官员提出了三个紧迫的问题。第一，此次疫情的病毒与以前见过的埃博拉病毒有多大的不同？第二，现有诊断试剂是否仍能检测到它？第三，现有治疗药物是否仍能对它提供保护？回答这些问题需要将新基因组与通过 NCBI Virus 和 Pathoplexus（与 NCBI Virus 同步）可获取的历史埃博拉基因组进行比较。但这并非可以轻松自动化，分析的前几步涉及在 Web 界面中手动点击、手动复现复杂的过滤器，并希望得到的数据集是完整和正确的。

这种工作流之所以如此难以自动化，是因为 NCBI Virus 的大部分过滤逻辑只存在于这个 Web 界面中。这对人类来说很烦人，对智能体来说更糟。如果研究者想要 2025 年发布的所有包含表面糖蛋白的 SARS-CoV-2 序列，一个经验丰富的病毒学家可能只需要在浏览器中点击几下。但以编程方式，它可能需要一个数百行的脚本，将多个 API（REST、Datasets、E-utilities）粘合在一起，逐页检索结果，协调标识符，并下载数百 GB 的数据，最终在本地过滤后丢掉大部分。

即使某个资源有 API，智能体可能仍然难以可靠地使用它，原因多种多样——例如 API 可能不暴露与 Web 界面相同的过滤语义，元数据字段可能文档不完善或标准化不一致，标识符可能在不同来源之间变化，或者"正确答案"可能依赖于专家人类知道但机器必须推断的约定。

## 当智能体尝试后的结果

为了更好地理解连接智能体和数据库的挑战，我们开发了一个测试，评估最先进的科学研究智能体（Claude、Biomni、Edison Analysis、GPT）在使用当今可用基础设施从 NCBI Virus 检索病毒序列时的能力。我们的基准测试 VirBench 包含 120 个真实的病毒序列查询，覆盖 40 种病原体，并有人工验证的基准真实计数。这些查询反映了在病毒监测、诊断试剂设计和蛋白质模型训练数据构建中出现的任务。例如，一个查询要求智能体"从 NCBI 检索 TaxID 3052462（Orthoebolavirus zairense (ZEBOV)）的病毒序列，需符合以下标准：宿主生物：人类，样本采集地理位置：非洲，采集日期在 2014 年 1 月 1 日或之后，采集日期在 2014 年 6 月 20 日或之前，最小序列长度：15,200 个碱基，最多 1,900 个模糊字符（N），排除实验室传代样本。"

当智能体被自行解决这些查询时，各系统的性能差异很大，并在较新的前沿模型中有显著改善。然而，即使是最强的模型也不能始终如一地达到可靠数据集构建所需的准确率和可复现性。Claude Sonnet 4、Claude Opus 4.7、Biomni、Edison Analysis、GPT-5.2-pro 和 GPT-5.53 的平均准确率从 16.9% 到 91.3% 不等。对于这些数据检索任务，有效标准是 100%：在某些情况下，一条缺失或错误的记录可能决定一个诊断试剂是否看起来覆盖了正在流行的变异株，或者一次疫情爆发被推断为比实际情况早或晚了几周开始。此外，同一个模型在三次被问同一个问题时往往产生截然不同的答案，削弱了可靠科学工作流所需的准确性和可复现性。对于上面示例的埃博拉病毒查询，Sonnet 4 在一次运行中返回了 106 条序列（预期：266），第二次返回了 15 条，第三次返回了 5 条，尽管每次收到的是完全相同的提示。

这种不一致性对下游分析有严重后果。我们使用上面显示的查询来检索埃博拉病毒序列并构建系统发育树——这是重建疫情期间病毒样本之间关系的标准分析。我们可以从系统发育树中获得的一个重要量是最 recent 共同祖先时间（TMRCA）的估计值。这是疫情爆发的推断根日期，可能改变关于病毒何时何地起源以及病毒传播了多久的结论。在这个案例中，从手动策划的 NCBI Virus 序列集构建的树恢复了 2014 年 1 月的 TMRCA，与 2014 年埃博拉病毒疫情爆发的[先前报告](https://www.science.org/doi/epdf/10.1126/science.1259657)一致（95% 最高后验密度区间跨越 1 月 27 日至 3 月 14 日）。相比之下，Sonnet 4 检索的三个序列集中有两个明显不完整，其中一棵树将推断的 TMRCA 推回到了 1922 年。剩下的数据集（运行 1）表面上看起来合理，但未能检索到来自几内亚的序列，并将估计的 TMRCA 推迟到了 2014 年 4 月，改变了关于疫情爆发时间的推断。

NCBI Virus 检索尝试之间的变异性还可能影响关于治疗药物的结论。我们检索了埃博拉病毒糖蛋白序列，以检查 maftivimab 和 MBP134 结合的表位——这两种抗体治疗药物是针对扎伊尔埃博拉病毒开发的，也是正在进行的埃博拉病毒疫情中的 [WHO 优先治疗候选药物](https://www.who.int/news/item/28-05-2026-experts-convened-by-who-advise-on-candidate-treatments-and-vaccines-for-ebola-disease-caused-by-bundibugyo-virus)。我们询问这些抗体靶向的区域中是否以前出现过突变。这种分析可以让研究者了解某种治疗药物是否会在病毒进化过程中继续保护患者。如果底层序列不完整或检索不正确，可能会使他们的结论产生偏差。在我们的例子中，Sonnet 4 检索的序列在第一次尝试时接近手动 NCBI 查询获得的结果。但在重复运行中，它遗漏了大部分突变残基。在第三次运行中，它突出显示了不同的一组残基，对这些目标区域的变异性产生了三种不同的印象。⁵

这两个例子都说明了科学中一个更广泛的模式：看起来像微小检索选择的细节可能改变生物学结论。在这个案例中，病毒序列检索中不一致的模型性能和失败模式的性质表明，大多数变异性可归因于基础设施的缺陷。智能体在未能检索大型结果集时计数不足，在过滤器应用不正确时计数过多。例如，与预期计数的最大偏差出现在有大量可用记录的病毒上，包括甲型流感、HIV-1 和 SARS-CoV-2，在这些情况下，在检索过程中中途停止和错误的下游过滤可能严重扭曲最终数据集。它们还在含义依赖于上下文、约定或信息存储位置的元数据字段上挣扎。随着查询变得更复杂，特别是超过三个或四个同时过滤器时，性能下降。

最终，智能体通常能够很好地理解任务并尝试执行，但它们缺乏可靠的机器可操作方式来执行、验证和重复。由此产生的答案可能看起来合理，但实际上是错误的，这尤其危险，因为序列检索通常是更长生物工作流中的第一步。

## 病毒数据检索的确定性层

> 关于 VirBench 和 gget virus 的更详细说明，请阅读[预印本](https://arxiv.org/pdf/2606.06749)。

为了将病毒数据检索转化为智能体和人类可以直接调用的功能，我们与 NCBI 的研究人员合作开发了 gget virus。起初，这似乎可能只是连接到正确 API 调用的简单问题。实际上，这要困难得多：NCBI Virus 是多个底层资源的门户，包括在美国、欧洲和日本维护的国际同步序列数据库，因此回答一个看似简单的查询通常需要从多个地方拼凑信息。

为了复现 NCBI Virus Web 界面的行为，gget virus 必须在其下面的不同系统之间协调，包括 REST、Datasets 和 E-utilities API。gget virus 决定哪些过滤器可以通过这些现有 API 应用，哪些必须在本地检查，因为 Web 界面暴露了无法从单一程序化端点获取的过滤行为。它处理批量检索，以便大型结果集（如 SARS-CoV-2 和甲型流感数据集）能被全面检索，而不是被任意截断。当过滤依赖于存储在单独数据库中的附加信息时——例如指示序列是否包含特定病毒蛋白的 GenBank 记录——gget virus 检索这些记录，使用它们应用过滤器，并在最终输出中保留相关的 GenBank 信息。然后它返回人和机器都可读的标准化输出，附带详细的日志，显示最终结果是如何产生的。⁶

当我们让智能体使用 gget virus 时，所有智能体的准确率都上升到了 90% 以上，GPT-5.5 达到了 99.7%。运行之间的变异性基本消除，模型间的性能差距大幅缩小。换言之，添加一个确定性检索层使得模型选择变得不那么重要了。考虑到可靠的数据集构建不应依赖于使用最新或最昂贵的模型，或知道哪个模型对特定数据库效果最好，这一点特别重要。相反，更便宜的模型配上正确的工具可以减少变异性并实现更广泛的访问。

gget virus 通过将复杂的、基于浏览器的检索工作流转化为准确且可复现的接口，使现有智能体在病毒数据检索方面更加可靠。回到我们步行城市的类比，这就像我们在步行基础设施下面修建了一条高速公路隧道，配有进出口匝道、顺畅运转的立交桥和与已知里程标记关联的出口编号。

## 正如 Karpathy 所说："让[基因组数据]对智能体可访问"

我们希望模型在生成假说、设计实验或推理机制时具有创造力。但创造力之下那层——基因标识符、模式、检索逻辑、坐标系统、元数据约定——应该是确定性的、可复现的、 boringly reliable 的。对于智能体可靠地支持科学发现，数据基础设施需要被设计为使其对智能体的支持与对人类的支持一样好。

这意味着将人类点击式工作流转化为可编程接口，将隐含约定转化为明确模式，并构建让智能体能够执行、验证和重复检索的确定性工具。gget virus 是这一方向的一个步骤，但它指向了一个更广泛的需求：如果我们想让 AI 智能体参与科学发现，从疫情应对到药物设计，我们需要构建可供智能体使用的生物数据基础设施，就像今天供人类使用的基础设施一样。
