# 如何构建 GPT Live — 让 AI 语音对话像真人一样的六个月工程

> 原文：[Continuous voice interaction with GPT Live](https://openai.com/index/continuous-voice-interaction-with-gpt-live/)
>
> 译者：Alice Larry（AI 翻译） | 审校：Colly Markus（AI 审校）

---

对于语音 AI 来说，知道什么时候该说话比听起来要难得多。人类说话者能在几分之一秒内自如地完成交替发言，但此前的语音 AI 系统跟不上这个节奏。它们的轮次架构依赖一种被称为"轮次检测器"（turn detector）的小型模型，后者面临着一个棘手的任务：猜得太早，用户被打断；猜得太晚，回应显得迟钝。只有在检测器做出决定之后，大得多的 LLM 才能开始工作。

[GPT-Live](https://openai.com/index/introducing-gpt-live/) 是我们的第三代语音系统，它将轮次检测器从音频路径中移除。其语音模型是全双工的，意味着它可以同时听和说。这消除了对单独检测器的需求，使对话感觉更即时、更自然。当需要更深入的推理或工具使用时，GPT-Live 还可以调用我们的前沿模型（如 GPT-5.5），而不会中断对话的流畅性。这些能力共同赋予 GPT-Live 前所未有的对话响应能力和智能水平。

在大规模上交付这一体验需要一个为低延迟优化的全新系统架构。与典型的请求-响应推理不同，我们的系统将传入音频流入语音模型，将输出语音流回用户，同时在单独的异步路径上处理委托。在过去六个月中，我们重新改造了模型推理、上下文管理和媒体传输，以保持语音从头到尾流畅流动。

该架构还在核心语音路径和应用逻辑之间创建了清晰的边界。这使得自定义应用行为变得容易，而不会影响响应速度。这一基础支撑着 ChatGPT 语音功能中日益丰富的能力，包括新推出的控制计算机和在 ChatGPT 桌面应用中协调代理的能力。

在这篇文章中，我们将解释为什么早期的轮次架构无法满足我们的需求，以及我们如何在每一层工程上为新系统优化响应速度。我们将涵盖有状态推理、动态上下文管理、异步委托和协议级优化——所有这些协同工作，使 GPT-Live 感觉真正"实时"。

## 从轮次交替到流式处理

早期的语音架构继承了文本 LLM 的轮次本质，但每个轮次表示为离散的音频块而非文本。在级联系统中，语音转文本、LLM 和文本转语音各自串行运行。这种顺序处理增加了延迟，并忽略了语气和节奏等线索。

语音到语音模型通过直接处理音频改进了这一方法。训练模型原生理解和生成语音使其能够保留在转录中丢失的细节并更快地响应。但系统仍然依赖轮次检测器来决定何时可以开始推理。模型处理了更多的交互，但交互仍然是基于轮次的。

GPT-Live 将语音模型置于对话的控制中心：音频流入和流出模型，而更深入的推理和工具使用异步发生。系统的主要工作是维持一个不间断的媒体循环。其他工作，如调用前沿模型和持久化对话，在实时路径之外完成。

## 实现持续推理

保持这个媒体循环不间断并不总是简单的。传输、处理或推理中的任何延迟都可能变成可听到的停顿或伪影。以前的轮次系统可以容忍音频块到达时间的一些变化。然而，实时媒体系统需要按时交付每一帧音频。

我们在 ChatGPT 语音和 Realtime API 上的早期工作为我们提供了重要的基础。我们已经[重建了语音基础设施](https://openai.com/index/delivering-low-latency-voice-ai-at-scale/)，以更低且更可预测的延迟直接在我们的系统内外流式传输音频和视频。GPT-Live 将该设计进一步推进，通过一个新的为持续对话构建的有状态推理系统，将媒体一直流式传输到模型。

流式推理只是解决方案的一部分。为了使其在生产环境中良好运行，我们还必须确保从客户端到推理栈的可靠音频交付，并解决有状态性的挑战。

我们做出的一个早期决定是特意将媒体流与应用和业务逻辑分离。音频在专用快速路径上在客户端和语音模型之间移动。委托、工具使用和其他应用工作在异步 RPC 边界之后完成。缓慢的工具调用或后端服务可以延迟其自身的结果，但不能阻止媒体流。

这种分离还为系统提供了清晰的自定义边界。应用可以更改其工具、策略和后端行为，而不会影响负责保持音频流动的媒体前端。实时路径保持小巧、可预测，并专注于必须在实时中完成的工作。

我们用 Go 语言编写了媒体前端和推理逻辑，替换了之前的 Python asyncio 实现。这显著改善了帧交付的平滑度——新系统的 p95 匹配了之前系统的 p50。

WebRTC 提供了传输基础。它专为低延迟媒体设计，可以在丢包、时钟漂移和客户端连接变化中继续运行。如果数据包迟到，WebRTC 可以巧妙地拉伸音频以防止间隙，然后短暂加速播放以赶回实时。

通过在整个系统中最小化缓冲和阻塞，我们能够交付人类对对话所期望的亚秒级响应速度。

### 保持（有状态的）对话继续

有状态推理有其自身的运营权衡。一个语音会话可能长时间保持活跃，但其上下文持续增长，而且模型实例根据需求上下旋转。

为了解决这些问题，我们构建了跨模型实例的无缝切换机制。当需要迁移时，我们可以在现有实例旁边预热一个替换模型实例，用当前会话上下文预填充它，并行运行两个实例的推理，然后在新实例完全就绪后切换。

同样的基本机制也支持动态上下文压缩。随着对话进行，其累积的上下文最终可能超出模型的上下文限制。压缩可以将上下文大小减小到限制范围内，但该操作需要时间。而且因为它改变了过去的上下文，它还会使模型的键值（KV）缓存失效——该缓存存储了之前处理过的 token 的注意力键和值。重建该状态需要新的预填充，引入额外的延迟。

相反，我们将压缩视为另一种受管理的迁移。当原始模型实例继续对话时，系统压缩上下文并准备一个使用新上下文的替换模型实例。一旦该实例就绪，我们就可以切换——没有任何媒体中断。这允许系统支持长时间运行的通话，在必要时进行压缩。

繁重的工作留在实时路径之外，因此即使在切换期间，对话也不会中断。

## 不阻塞对话的委托

GPT-Live 调用现有前沿模型的能力赋予了它强大的功能，有效地将"说话"与更深层的"思考"解耦。但使这种双模型架构感觉像一个系统需要解决两个相关的工程问题。

### 为更深层的工作委托

GPT-Live 提供快速、自然的回应，同时 GPT-5.5 在后台处理搜索。

使用 GPT-Live-1 的示例对话，调用 GPT-5.5 Instant。

首先，结果必须在足够短的时间内返回以便在正在进行的对话中有用，因此我们必须最小化整个委托路径上的延迟——从路由、提示词处理到推理和工具调用。同时，产品中其他地方的系统仍然需要离散的消息，因此我们必须以一种它们能理解的形式表示正在进行的对话。

## 使委托快到感觉自然

当委托被分派时，我们优化的是从前沿模型产生对对话有用的内容之前的时间。语音模型可以在前沿模型推理或使用工具时短暂维持对话的进行，但它无法隐藏任意慢的响应。因此，我们将完整的委托环路——路由、提示词处理、推理和工具调用——视为响应速度预算的一部分。

第一个优化是在委托请求之前设置好前沿模型及其需要的任何工具。当语音会话开始时，应用服务器为前沿模型创建推理会话，并用初始对话上下文预填充它，确保提示词在第一次委托请求之前已被完全处理。

然后，我们在语音对话期间保持该推理会话可用，并为连续请求使用稳定的会话亲和性。结合 prompt 缓存，这些技术改善了延迟，同时工作节点故障仍然可以轻松恢复。

推理努力、输出限制、工具架构和模型-工具往返也会影响对话何时收到有用的结果，我们调整了这些杠杆以获得更快的响应。通过最小化委托路径上所需的工作，我们使语音模型能够快速整合前沿模型的结果。

### 从连续语音中提取离散轮次

尽管语音模型在连续的语音流上运行，但其周围的许多系统仍然在用户和助手的轮次上运行——包括 ChatGPT 的对话 UI 和我们部分分析及安全基础设施。因此，应用服务器将重叠的、偶尔模糊的对话拆解为离散消息。

当音频到达时，服务器使用部分转录和时间信号来推断哪位说话者拥有发言权，并构建消息队列。最新的消息保持暂时状态——其文本、时间和说话者归属都可能随着更多语音到达而改变。一旦说话者持续拥有发言权的时间足够长，使归属可靠，服务器就会最终确定相应的消息。

说话者重叠使这变得更加复杂。助手在用户说话时的简短确认（例如"嗯嗯"或"好的"）不应一定成为独立的消息。然而，实质性的助手插话通常应该成为独立消息。同样，我们优先考虑显示的助手回应的连贯性，即使用户在中间插话。

每种分段策略都在新鲜度和确定性之间做权衡。过早提交会产生碎片化的历史和不稳定的排序；等待太长会延迟转录和依赖它的功能。因此，系统维护两个相关的对话视图：当前状态的推测视图和所说内容的权威记录。应用 UI 中的对话视图可以处理更新，因此它使用推测视图。但分析管线的日志记录需要最终转录。

这赋予了 ChatGPT 其余部分对话交换的稳定视图，而不会在实时语音路径上强加轮次交替。

## 用更快的协议启动会话

响应速度从用户点击按钮的那一刻就开始了。使用 GPT-Live，系统必须建立媒体路径并在对话开始之前开始将音频馈入模型。这使得启动序列的每个部分都处于关键路径上。

如上所述，WebRTC 提供了强大的实时基础，但启动一个原生 WebRTC 会话需要数量惊人的协议握手和网络往返。WebRTC 早于后来塑造 QUIC 等协议的减少往返的重点。因此，其底层协议在一起使用时有时会重复工作。例如，每个协议都包含自己的反 DoS 机制，即使在完整 WebRTC 协议栈上下文中并不需要时也是如此。

我们分析了协议栈并开发了 WebRTC Abridged Roundtrip Protocol（[WARP](https://datatracker.ietf.org/doc/draft-uberti-tsvwg-warp/)），将媒体和数据启动从 6 次网络往返减少到仅 1 次。WARP 通过一组向后兼容的协议改进实现这一点：将 DTLS 握手搭载在 ICE 之上（[SPED](https://datatracker.ietf.org/doc/draft-hancke-webrtc-sped/)）、使用更快的 [DTLS 1.3](https://www.rfc-editor.org/rfc/rfc9147.html) 握手、预协商 SCTP 握手（[SNAP](https://datatracker.ietf.org/doc/draft-hancke-tsvwg-snap/)），以及预协商数据通道而非使用 [DCEP](https://www.rfc-editor.org/rfc/rfc8832.html)。

我们将 WARP 设计为一组开放规范，与 WebRTC 社区的合作者共同开发，以便更广泛的生态系统能从这项工作中受益。我们正在通过 IETF 的 TSVWG 工作组推进这些提案，WARP 支持已经被添加到 libwebrtc 和 Pion 中，其他 WebRTC 实现的工作也在进行中。

在优化媒体握手之后，仍然存在一个突出的延迟：用于在 WebRTC 连接之前共享 SDP 参数的信令交换。为了将此交换从关键路径上移除，我们开发了所谓的 Instant Connect。它提前协商这些参数而不预留服务器容量，且不需要对现有 WebRTC 实现做任何更改。

Instant Connect 与标准信令流程并行运行。如果预协商的参数有效，服务器可以在第一个媒体包到达时实例化会话。如果它们已过期或无效，信令流程已经在进行中，因此客户端可以回退而不会产生额外延迟。

Instant Connect 和 WARP 共同大幅减少了从用户意图到实时媒体流的时间。随着 SDP 交换移出关键路径且 WARP 压缩了传输握手，客户端现在可以用一个 UDP 数据包启动会话。服务器可以立即响应，让系统的其余部分开始做用户真正关心的工作：听和回应。

## 在生产中安全测试 GPT-Live

一个系统在纸面上可能看起来很快，但在真实的语音流量下仍可能停滞。在让 GPT-Live 与用户对话之前，我们运行了一次静默测试，将一小部分且逐渐增加的生产 ChatGPT 语音会话流量同时路由到现有的 Advanced Voice Mode 体验和我们的新系统。Advanced Voice Mode 继续像往常一样为用户服务，而影子路径以只读模式运行推理。这使系统暴露于真实的客户端、网络、会话长度和地理分布，而不会改变用户听到的内容。

首批经验训之一是容量不能简单归结为 GPU 吞吐量。语音会话保持开启并持续发送帧，因此 CPU 端的流处理器、队列和网络路径必须与推理一起扩展。在真实负载下，一个支持组件比我们的负载测试预测更早达到饱和，导致推理请求积压和延迟叠加。我们将容量问题从"一个 GPU 能处理多少请求？"更改为"系统在保持每帧按时交付的同时能维持多少并发会话？"

测试还使地理分布成为一阶关注点。将一个会话路由到远处的容量可能在启动和流式传输期间的多个节点增加延迟。我们开始将模型发布与区域容量和流量引导配置一起验证，然后按来源地理区域分解延迟。将推理移近用户有所帮助，但它也强化了更广泛的教训：端到端响应速度取决于路径中的每个服务，而不仅仅是模型服务器。

其他故障仅在真实的会话生命周期中出现。长时间运行的会话暴露了内存和持久化压力。重连测试了压缩和状态恢复。普通的客户端断开连接揭示了关闭握手中的竞争条件。这些问题在短时间负载测试中很少出现，因为它们依赖于时间、累积的状态和跨服务边界的行为。

最后，生产测试迫使我们改善可观测性和发布控制。我们发现混合了不同延迟来源的指标、聚合隐藏了个别不健康引擎的仪表板，以及测试和部署系统之间的配置漂移。作为回应，我们添加了更精细的遥测、对已知良好配置的验证、分阶段放量，以及快速隔离或禁用单个路径的能力。静默测试成为了早期发布的排练，不仅针对系统可以接受多少流量，还针对我们能多快检测、控制和恢复故障。

## 从客户端到模型，全程响应

将 GPT-Live 带到 ChatGPT 规模需要一个围绕一个基本原则构建的全新系统：**语音必须流畅**。流式推理为全双工模型提供持续的音频供应。专用媒体路径确保可靠的帧交付。异步委托让更深层思考并行运行。优化的传输使体验一路响应到用户。

GPT-Live 背后的架构正在成为实时交互的更广泛平台。它支撑着 ChatGPT 语音从对话扩展到代理协调，并将为即将推出的 GPT-Live API 提供基础。随着时间推移，它将允许语音体验跨越更多设备、应用和模态，而不牺牲使语音对话感觉"实时"的那种即时性。
