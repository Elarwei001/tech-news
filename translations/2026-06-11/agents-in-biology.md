# 为生物学中的智能体铺路

**作者**：Laura Luebbert。基于 [Ferdous Nasri、Sarah Gurev、Patrick Varilly、Krithik Ramesh、Nuala A. O'Leary、Jonah Cool、Bernhard Y. Renard、Pardis Sabeti 和 Laura Luebbert](https://arxiv.org/pdf/2606.06749) 的研究。

在这篇文章中，Laura Luebbert 主张我们需要让生物数据基础设施对智能体更加友好。作为案例研究，她和她的团队让科学研究智能体（Claude、Biomni 开源版（Biomni OSS）¹、Edison Analysis²、GPT）从 NCBI Virus（病毒学家用于监测和诊断分析方法开发等任务的数据库）中检索序列数据。即使是最强的模型也无法稳定达到可靠数据集构建所需的准确度。但一旦她和她的团队添加了 gget virus——一个确定性检索层，准确率就上升到了近 100%。对科学智能体而言，更广泛的启示是：确定性检索工具（目前）对于使智能体工作流更加可靠至关重要，而生物数据库需要将智能体视为规模化用户来重新设计。

用 AI 智能体来导航生物数据基础设施，就像驱车穿过一座在汽车发明之前设计的老城：基础设施可能很精美甚至经过深思熟虑，但到处都是狭窄、蜿蜒的街道，难以让现代车辆通行（异构的文件格式、分散的数据库、一次性的检索脚本）。³ 你可以给城市加装交通标志、停车场和偶尔拓宽的道路，但基本布局仍然难以导航，因为它原本是为另一种交通方式设计的。相比之下，软件基础设施基本上是为汽车（智能体）的需求量身打造的：铺设的道路、清晰的车道、标准化的信号，以及为从起点到终点的快速通行而设计的系统（版本控制、文档齐全的 API 和包管理器）。

因此，编码智能体的进步远快于生物智能体。软件通常提供结构化的数字工作流和可靠的接口，而生物信息学计算所需的数据检索和验证基础设施通常脆弱、异构且依赖特定流程。我们导航这些基础设施的工具必然是定制的，针对特定领域或假设进行调优。此外，软件提供可测试的输出，可以快速编译和验证（例如，通过生成一个能通过项目测试的补丁来解决 GitHub issue），而生物学提供的可简单验证且有意义的奖励信号却很少。

因此，生物智能体的瓶颈不仅是推理能力，更在于缺乏广泛的确定性执行层来查询生物数据。科学家可以表达他们的意图（例如，找到所有具有该结构域的人类激酶并提取它们的结构），但智能体通常缺乏可靠的方式来访问包含所需信息的数据库。

在生物和科学工作流中，即使是很小的错误也可能产生严重后果。例如，从错误的基因组构建版本检索坐标可能使下游的生物学解释无效。无意中混淆 RefSeq 和 GenBank 记录、将部分基因组当作完整基因组处理、在分段病毒中混淆片段名称，或因元数据字段不一致而遗漏相关记录，同样会造成严重后果。研究的美与挑战在于，细节往往至关重要。

就像驱车穿越意大利的山城一样，如果街道太窄、转弯太急、路线依赖当地知识，那么车再强大也没用。如果我们希望智能体帮助实现科学发现——从疫情应对到药物设计到生物建模——我们需要构建让它们能像人类一样可靠导航的生物数据基础设施。

## Karpathy 关于 Web 开发的演讲告诉我们在 AI 智能体时代做生物学的启示

智能体需求与人类构建的工具之间的不匹配并非生物学独有。无论在哪里将智能体插入仅为人类使用而设计的环境中，都会出现同样的摩擦。

几个月前，Andrej Karpathy [做了一次演讲](https://www.youtube.com/watch?v=LCEmiRjPEtQ)，谈论 AI 时代的软件，最后抱怨了一些听起来非常耳熟的事情。他用"氛围编码"做了一个小型 Web 应用，但当他想让它真正投入运行（认证、支付、部署）时，他花了一周时间在浏览器仪表盘中点击。

正如他总结的："代码是最简单的部分！大部分工作都在浏览器里点击各种东西。"文档不断告诉他"去这个 URL，点击这个下拉菜单"。他的结论是没有人应该这样做。相反，我们必须为智能体而构建。

Karpathy 在软件智能体世界中经历的，正是生物学研究人员长期以来的困扰：试图让智能系统在围绕异构信息、隐含约定和人类浏览器点击而构建的环境中运行的痛苦。

## 案例研究：病毒学中的"点击税"

早在 AI 智能体出现之前，计算生物学家和遗传学家就已经开始为传统计算生物学生产工具，逐步解决这个问题。Biopython、BioPerl、BioJulia、Entrez Direct、BioMart、gget 等许多工作流库都是将生物数据从浏览器界面移到研究人员可以直接计算的地方的努力。

问题是生物数据并不存在于一个有着统一接口的单一数据库中。它是一个杂乱的道路网络，每条路都有自己的标识符、约定、格式、过滤逻辑和程序化访问程度。有些数据很容易通过编程方式访问。其他的就没那么简单了。

病毒学是更困难的案例之一。从疫苗和诊断分析设计到蛋白质模型训练数据构建的研究工作流，通常始于从 NCBI Virus 检索序列——这是一个可搜索的 Web 界面背后的病毒序列记录集合，数据来源于 GenBank、RefSeq 和国际 INSDC 生态系统（包括 Pathoplexus）。作为构建病毒疫情监测工具的研究人员，我们亲身体会到这些检索背后隐藏了多少专业知识。在病毒学实验室中，NCBI Virus 的数据集整理说明通常以一长串复杂过滤器的形式流传，用户必须在 Web 界面中手动重现：正是 Karpathy 抱怨的那种浏览器点击工作流。

当前由 Bundibugyo 病毒引起的埃博拉疾病疫情（发生在刚果民主共和国）是一个严峻的例子，说明为什么简化的病毒数据访问可能具有真实的生死攸关的后果。2026 年 5 月 14 日，刚果（金）金沙萨的国家生物医学研究所（INRB）分析了 13 份血液样本，并于次日确认其中 8 份为 Bundibugyo 病毒疾病阳性，⁴ 随后宣布了埃博拉疫情暴发。截至 5 月 29 日，WHO 已报告刚果（金）有超过 1,000 例确诊和疑似病例，包括超过 200 例死亡。研究人员还生成了首批接近完整的疫情基因组，帮助确定此次疫情是由一次新的溢出事件引起的。

这些基因组给公共卫生官员提出了三个紧迫的问题。第一，此次疫情病毒与之前见过的埃博拉病毒有多大差异？第二，现有诊断方法是否仍能检测到它？第三，现有治疗方法是否仍能对抗它？回答这些问题需要将新基因组与通过 NCBI Virus 和 Pathoplexus（同步到 NCBI Virus）可获取的历史埃博拉基因组进行比较。但这并不是轻易可以自动化的——分析的前几步涉及在 Web 界面中手动点击、手工重现复杂的过滤器，并希望最终的数据集是完整和正确的。

这个工作流之所以难以自动化，是因为 NCBI Virus 的大量过滤逻辑仅存在于其 Web 界面中。这对人类来说很烦人，对智能体来说则更糟。如果研究人员想要 2025 年发布的所有包含表面糖蛋白的 SARS-CoV-2 序列，经验丰富的病毒学家可能只需在浏览器中点击几下。但以编程方式实现，可能需要一个数百行的脚本，将多个 API（REST、Datasets、E-utilities）粘合在一起，逐页检索结果，协调标识符，下载数百 GB 的数据，然后在本地过滤后丢弃大部分。

即使某个资源有 API，智能体仍然可能因各种原因难以可靠地使用——例如 API 可能不暴露与 Web 界面相同的过滤语义，元数据字段可能文档不完善或标准化不一致，标识符可能在不同来源之间变化，或者"正确答案"可能依赖于专家人类知道但机器必须推断的约定。

### 当智能体尝试时会怎样

为了更好地理解桥接智能体与数据库的挑战，我们开发了一个测试，评估最先进的科学研究智能体（Claude、Biomni OSS、Edison Analysis、GPT）在被要求使用现有基础设施从 NCBI Virus 检索病毒序列时的能力。我们的基准测试 VirBench 包括 120 个现实的病毒序列查询，涵盖 40 种病原体，具有人工验证的真实计数。这些查询反映了病毒监测、诊断分析设计和蛋白质模型训练数据构建中出现的任务。例如，一个查询要求智能体"从 NCBI 检索 TaxID 3052462（Orthoebolavirus zairense（ZEBOV））的病毒序列，需满足以下条件：宿主生物：人类，样本采集地理位置：非洲，采集日期在 2014 年 1 月 1 日或之后，采集日期在 2014 年 6 月 20 日或之前，最小序列长度：15,200 个碱基，最多 1,900 个模糊字符（N），排除实验室传代样本。"

当智能体被要求独立解决这些查询时，不同系统之间的表现差异很大，但在更新的前沿模型中有显著改善。然而，即使是最强的模型也无法稳定达到可靠数据集构建所需的准确度和可重复性。Claude Sonnet 4、Claude Opus 4.7、Biomni OSS、Edison Analysis、GPT-5.2-pro 和 GPT-5.55 的平均准确率从 16.9% 到 91.3% 不等。对于这些数据检索任务，标准实际上是 100%：在某些情况下，一个缺失或不正确的记录可能决定诊断分析是否看起来覆盖了流行的病毒多样性，或者疫情是否被推断为比实际情况更早或更晚开始。此外，同一模型在三次被问及同一问题时经常产生截然不同的答案，破坏了可靠科学工作流所需的准确性和可重复性。对于上述埃博拉病毒查询示例，Sonnet 4 在一次运行中返回了 106 条序列（预期：266 条），第二次返回 15 条，第三次返回 5 条，尽管每次收到的提示完全相同。

这种不一致对下游分析有影响。我们使用上述查询检索埃博拉病毒序列并构建系统发育树——这是重建疫情期间病毒样本关系的标准分析。系统发育树可以得到的一个重要量值是最近共同祖先时间（TMRCA），即推断的疫情根源日期，这可能改变关于病毒何时何地起源以及传播了多久的结论。在这个案例中，使用人工整理的 NCBI Virus 序列集构建的树恢复了 2014 年 1 月的 TMRCA，与[之前的报告](https://www.science.org/doi/epdf/10.1126/science.1259657)一致（95% 最高后验密度区间跨越 1 月 27 日至 3 月 14 日）——针对 2014 年埃博拉疫情。相比之下，Sonnet 4 检索的三个序列集中有两个明显不完整，其中一个树将推断的 TMRCA 推回到了 1922 年。剩余的数据集（运行 1）表面上看起来合理，但未能检索到来自几内亚的序列，并将估计的 TMRCA 推迟到 2014 年 4 月，改变了推断的疫情时间线。

智能体在 NCBI Virus 检索尝试之间的变异性也可能影响关于治疗方法的结论。我们检索了埃博拉病毒糖蛋白序列，以检查 maftivimab 和 MBP134 结合的表位——这是针对扎伊尔埃博拉病毒开发的抗体治疗方法，也是正在进行的埃博拉疫情中 [WHO 优先推荐的治疗候选药物](https://www.who.int/news/item/28-05-2026-experts-convened-by-who-advise-on-candidate-treatments-and-vaccines-for-ebola-disease-caused-by-bundibugyo-virus)。我们询问这些抗体靶向的区域中以前是否出现过突变。这种分析可以让研究人员了解随着病毒进化，治疗方法是否仍能保护患者。如果底层序列不完整或获取不正确，可能会偏离他们的结论。在我们的例子中，Sonnet 4 检索的序列在第一次尝试中接近手动 NCBI 查询获得的结果。在重复运行中，它遗漏了大多数突变残基。第三次运行中，它突出显示了一组不同的残基，对这些靶区域的变异性产生了三种不同的印象。

这两个例子说明了一个更广泛的科学模式：看起来是微小检索选择的细节可以改变生物学结论。在这个案例中，模型在病毒序列检索中不一致的表现以及失败模式的性质表明，大多数变异可归因于基础设施的不足。智能体在无法检索大型结果集时计数偏低，在过滤器应用错误时计数偏高。例如，与预期计数的最大偏差出现在有大量可用记录的病毒中，包括甲型流感、HIV-1 和 SARS-CoV-2——在这些情况下，检索中途停止和下游过滤不正确会大幅扭曲最终数据集。它们还在含义依赖于上下文、约定或信息存储位置的元数据字段上遇到困难。随着查询变得复杂，特别是超过三四个同时过滤器时，性能会下降。

最终，智能体通常对任务的理解足以尝试执行，但缺乏机器可执行的方式来完成、验证和重复。由此产生的答案可能看起来合理但仍可能是错误的——这尤其危险，因为序列检索通常是更长的生物工作流中的第一步。

### 病毒数据检索的确定性层

有关 VirBench 和 gget virus 的更详尽解释，请阅读[预印本](https://arxiv.org/pdf/2606.06749)。

为了将病毒数据检索变成智能体和人类可以直接调用的功能，我们与 NCBI 的研究人员合作开发了 gget virus。起初，这似乎只是连接到正确的 API 调用的简单事情。实际上要困难得多：NCBI Virus 是多个底层资源的门户，包括在美国、欧洲和日本维护的国际同步序列数据库，因此回答一个看似简单的查询通常需要从多个地方拼凑信息。

为了重现 NCBI Virus Web 界面的行为，gget virus 必须在它下面的不同系统之间协调，包括 REST、Datasets 和 E-utilities API。gget virus 决定哪些过滤器可以通过这些现有 API 应用，哪些必须在本地检查——因为 Web 界面暴露了无法从单一程序化端点获取的过滤行为。它处理批处理，使大型结果集（如 SARS-CoV-2 和甲型流感数据集）能被全面检索而非任意截断。当过滤依赖于存储在单独数据库中的额外信息时（例如 GenBank 记录指示序列是否包含特定病毒蛋白），gget virus 检索这些记录，使用它们应用过滤器，并在最终输出中保留相关的 GenBank 信息。然后它返回人和机器都可读的标准化输出，附带详细日志显示最终结果是如何产生的。⁸

当我们让智能体访问 gget virus 时，所有智能体的准确率都上升到 90% 以上，GPT-5.5 峰值达到 99.7%。运行间变异性基本消除，模型之间的性能差距大幅缩小。换句话说，添加确定性检索层使模型选择变得不那么重要。考虑到可靠的数据集构建不应依赖于拥有最新或最昂贵的模型，或者了解哪个模型对给定数据库效果最好，这一点尤其重要。相反，较便宜的模型配合正确的工具可以减少变异性并扩大访问范围。

gget virus 通过将复杂的基于浏览器的检索工作流转化为准确且可重复的接口，使现有智能体在病毒数据检索方面更加可靠。回到我们步行城市的类比，这就像我们在步行基础设施下方添加了一条高速公路隧道，配有出入口匝道、流畅运转的立交桥和与已知里程标记关联的出口编号。

### 正如 Karpathy 所说："让[基因组数据]对智能体可访问"

我们希望模型在生成假设、设计实验或推理机制时发挥创造力。但创造力之下那一层——基因标识符、模式、检索逻辑、坐标系统——应该是确定性和可重复的。实现这一点既需要为现有数据库构建更好的工具层，也需要设计下一代数据库时就考虑智能体作为规模化用户的需求。gget virus 是朝这个方向迈出的一步，展示了当我们在智能体和它们需要导航的基础设施之间放置正确的接口时会发生什么。
