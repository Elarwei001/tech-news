# GPT-5.6 如何融合前沿智能与前沿效率

> 原文：[How GPT-5.6 fuses frontier intelligence with frontier efficiency](https://openai.com/index/gpt-5-6-frontier-intelligence-efficiency/)
>
> 翻译：Alice Larry *(AI 译)* | 审校：Colly Markus *(AI)*

---

我们将 GPT-5.6 模型家族设计为在[能力与成本](https://openai.com/index/gpt-5-6/)之间取得平衡，覆盖用户使用我们模型的各种任务。我们的旗舰模型 GPT-5.6 Sol 在最大推理设置下于 Artificial Analysis Coding Agent Index 上超越 Claude Fable 5，成本不到其一半。Terra 以 GPT-5.5 一半的价格达到同等智能水平，而 Luna 是我们最快、最经济的模型，定价比 Sol 便宜 80%。为实现这些效率提升，我们的研究和技术团队在技术栈的每个主要层级做出了重大优化。这些改进横跨模型、推理（我们如何运行模型以生成输出）以及我们的代理框架——Codex 和 ChatGPT Work 都在使用这个框架。

在过去四年中，随着我们将模型规模扩展到 10 亿活跃用户和超过 200 万家企业，效率一直是我们将智能普惠化的核心。我们的使命是确保通用人工智能造福全人类。这些年来，我们持续在技术栈各层解锁更大的优化，以在每个成本-智能曲线节点上提供最高性能的模型。通过 GPT-5.6，我们实现了有史以来最高的每 token 智能效率，该模型经过训练以[在每个 token 中完成更多工作](https://openai.com/index/gpt-5-6/)。在训练中，我们同时优化任务成功率和效率，引导模型以更直接的路径完成任务。

本文探讨的是模型之外的内容，分享我们如何通过两大主要技术栈层面的进展实现效率设计：1）推理，通过优化负载均衡、推测解码、缓存和内核优化等流程，从相同硬件中获得更多输出；2）代理框架，包括更好地管理上下文膨胀、工具使用和重复工作。我们还将分享 GPT-5.6 Sol 在自主实现这些增益方面的作用。虽然任何单独的改进看似有限，但这些收益复合叠加，使我们能够在智能和效率两方面同时处于前沿。

## 用 GPT-5.6 Sol 加速推理

在一个计算受限、模型需求增长快于产能的世界中，效率是每个系统设计的核心。我们的推理栈尤其如此——它运行训练好的模型来生成响应。我们的主要目标是在相同硬件上提供更多 token，同时保持用户期望的智能、延迟、可用性和可靠性。

实现这一点需要优化整个系统。一个模型在隔离状态下可能高度高效，但如果请求分配不当、硬件闲置或数据移动拖慢计算，服务成本仍然会很高。每一层的改进都会复合叠加——增益来自路由（请求发送到哪里）、调度（请求何时发送）、内核（在 GPU 上运行的软件）、缓存（保存和重用工作）和模型实现（GPU 代码的排列顺序）等方面的优化。GPT-5.6 Sol 在 Codex 中在所有这些优化中发挥了关键作用。

第一个重要例子是负载均衡。在全球范围内，我们根据地理位置、可用容量和加速器类型（运行模型的 GPU 或专用芯片类型）来路由请求。在集群内部，我们根据负载、上下文长度、缓存可用性和其他请求属性在模型实例间分配工作。在每个实例内部，工作必须在加速器、模型子网络和计算核心之间高效分区。GPT-5.6 Sol 在 Codex 中帮助我们分析生产流量、识别此前被忽视的不平衡来源、测试新的路由策略，并持续调优这些启发式规则。仅负载均衡方面的改进就大幅降低了模型服务成本。

我们还利用 GPT-5.6 Sol 来优化模型的前向传播：将输入转化为下一个 token 预测的计算。即使单个操作很快，过多的内存移动、同步和低效的数据布局也会使 GPU 闲置。为避免这一点，GPT-5.6 Sol 找到了可以预计算、避免或并行化的工作。在 Codex 中，GPT-5.6 Sol 自主重写和优化了我们的生产内核——构成模型数学操作的核心代码。这一工作之所以成功，部分是因为我们已训练 GPT-5.6 使其擅长用 [Triton](https://triton-lang.org/main/index.html) 和 [Gluon](https://triton-lang.org/main/gluon/index.html)（OpenAI 维护的两种开源 GPU 编程语言）编写和改进内核。这些努力加上 GPT-5.6 Sol 更广泛的内核改进，将端到端服务成本降低了 20%。我们还大量投资于验证工具，如开源工具 [FpSan](https://triton-lang.org/main/programming-guide/chapter-3/fpsan.html)（浮点数消毒器），帮助验证 GPT-5.6 Sol 编写的内核的正确性。

推测解码是提升速度和效率的另一个杠杆。该技术涉及在主模型旁边运行一个较小的草稿（或"推测器"）模型，由推测器提出若干 token 供主模型并行验证。当这些提议被接受时，系统可以从一次主模型前向传播中产出多个 token，减少昂贵的顺序计算。GPT-5.6 Sol 通过设计和运行数百项架构实验来改进自己的草稿模型，测试大小、结构和特征方面的变化。此外，GPT-5.6 Sol 启动并监控了推测器训练过程，在出现硬件故障和训练不稳定等问题时自主干预。由此带来的改进将 token 生成效率提高了 15% 以上。

在处理未缓存的输入 token 时，模型在一个计算密集型的前向传播中构建键值（KV）缓存；在生成输出时，它反复读取并扩展该缓存。最优的服务配置——如批处理、分片和 KV 管理——在很大程度上取决于工作负载特征——提示词和输出长度、批次大小、缓存命中率、查询特性等。然而，配置空间此前太大，无法系统调优，迫使工程师依赖宽泛的启发式规则。借助 Codex 中的 GPT-5.6 Sol，我们能够分析生产工作负载、生成和评估候选配置，并为每种场景超优化引擎和模型的配置方式。这使得前所未有的工作负载级优化成为可能，从相同硬件中提取更多有效推理。

推理优化是一个持续的反馈循环。我们测量生产行为，识别最大差距，实施变更，并验证这些变更改进的是整个系统而非孤立基准。GPT-5.6 Sol 和 Codex 加速了这个循环的每个环节。这意味着我们的团队可以探索更多想法、更快地响应不断变化的工作负载，并打造出更低延迟、更大容量、更低用户成本的推理栈。

## 我们的代理框架如何精简重复工作

ChatGPT Work 和 Codex 通过一系列模型请求和工具调用来完成复杂任务。在一个回合中——从用户请求到最终响应——Codex 可能需要检查源代码、搜索部署历史、阅读事故报告、编辑文件和运行测试。每一步都可能需要一次请求。

准备上下文、传输数据、运行推理、调用工具和启动流程都需要时间和计算。如果一个任务需要 30 次模型请求，每多一秒都会累积。提升整体性能意味着减少整个系统中的重复工作，而不仅仅是让模型更快。

一个用户回合可能包含多次模型和工具迭代。在重复区域内的任何成本都可能被多次支付。

这些乘数效应指导了我们代理框架的设计——它是一个 Rust 编排层，连接我们的模型、工具和用户环境。接下来，我们将介绍如何通过避免上下文膨胀、加载工具和重用工作来提高每次请求的效率。

#### 避免上下文膨胀

随着代理获得对更多工具、技能、插件和对话历史的访问权限，上下文窗口很容易膨胀。这会增加成本、分散模型注意力并引发不必要的推理。框架可以通过延迟发现来减少这种开销——使集成、自定义 MCP 工具、技能和插件仅在需要时才可被发现。框架还防止单个工具和 MCP 集成意外占用上下文窗口。工具输出默认上限为 10,000 个 token，除非模型请求不同的限制。

#### 保留精确前缀以优化 prompt 缓存

如前所述，代理循环可以在单个回合内将相同的指令、对话历史、工具定义和早期结果多次发送到 GPU。处理这些重复输入是昂贵的，因此 prompt 缓存会重用与先前处理过的提示词前缀相关的计算。为保留该前缀，框架将所有模型可见的历史记录视为仅追加：新的消息、工具结果和环境更新会被添加到末尾，而不是插入到之前的上下文中。工具也以确定性顺序呈现，而运行时设置（如审批策略）在执行期间应用，而不是嵌入到工具定义中。这一设计选择有助于 Codex 和 ChatGPT Work 保持较高的整体 prompt 缓存命中率。

增量传输改变了跨网络传输的内容；prompt 缓存改变了模型可以避免重新计算的内容。宽度为概念性的，额外的压缩层未显示。

## 智能曲线上的效率

我们在 GPT-5.6 中实现的效率提升是技术栈各层（涵盖研究、推理和代理框架）多年复合改进的结果。GPT-5.6 在实现许多这些改进方面发挥的作用，让我们对优化步伐的加速充满乐观。我们将继续在内核优化等领域做出更大改进，同时对技术栈进行基础性升级。我们期待将这些持续的底层改进以更广泛可用、更具成本效益的智能形式回馈给我们的用户和客户。
